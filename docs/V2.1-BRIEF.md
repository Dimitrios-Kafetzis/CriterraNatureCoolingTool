# v2.1 Brief — Map-based Site Selection and Parameter Autofill

The implementation brief for the last of the three post-v1 review releases
(D-038), written now so the next session implements against settled contracts
rather than re-designing mid-flight. Companion to [DECISIONS.md](DECISIONS.md)
(D-038 schedules the release; D-046 records its scope) and
[V2-VISION.md](V2-VISION.md).

**Status: proposal. Nothing is implemented and three decisions are open.** The
first of them is not a detail — it is a head-on collision between what a map
picker needs and a rule this project has treated as absolute since D-030.

## Starting state

v2.0 shipped at methodology `2026.08.04` with 110 typologies over 18 cited
archetypes, packages, and availability gating. The questionnaire asks about 45
questions across six steps. Nothing in the application makes a third-party
network request: fonts, brand assets and the frontend build are all self-hosted,
and CI enforces it (D-030, D-035, D-036).

Review comment 7 asked for map-based site selection with parameter autofill.
D-038 placed it **last** deliberately: autofill must target the questionnaire
v2.0 leaves behind, not the one v1.1 shipped. That condition is now met.

## What a map can honestly fill in

This is the release's central question, and the answer is narrower than the
feature name suggests. Three inputs can be derived from a point or a polygon on
a map without inventing anything:

| Input | Source | Nature of the derivation |
|---|---|---|
| `site_area_m2` | the drawn polygon | **Pure geometry.** No dataset, no inference, no uncertainty beyond the user's own drawing. |
| `country` | a bundled country-boundary dataset | **Point-in-polygon.** Deterministic given the boundary data; feeds only the emission-factor and currency defaults. |
| `climate_zone` | a bundled Köppen–Geiger classification | **A cited lookup, plus a documented mapping.** The tool has six zones; Köppen–Geiger has thirty. The mapping is a methodology value and needs a citation and a version bump. |

### What the map must NOT fill in, and why that matters

Everything else the questionnaire asks about the site — canopy cover, green
cover, imperviousness, LST anomaly, land use, shade level, population density,
vulnerable-population presence — **requires satellite or census data, which is
the GIS workflow deferred from v1 by D-002 and scoped as a separate wave in
[V2-VISION.md](V2-VISION.md).**

The temptation here is obvious and should be named: a map that fills in canopy
cover from a quick NDVI lookup would demo extremely well. It would also produce
the tool's most decision-relevant site inputs from an unvalidated pipeline, with
no evidence table behind it and no confidence treatment — which is the same
defect D-016 refused for cost defaults, in a new place. **This release fills in
three inputs and says plainly that it fills in three.**

## Three decisions that need rulings

### Decision 1 — The basemap, and the no-third-party-request rule

A map picker needs a basemap. Useful zoom levels need tiles. Tiles come from a
tile server. **Every option here breaks something.**

| Option | What it costs |
|---|---|
| **(a) No basemap** — draw on a blank canvas over bundled coastlines and country outlines | Honest and offline, but nobody can find their street corner at zoom 4. This is not a site picker; it is a coordinate entry field with decoration. |
| **(b) Bundled low-zoom vector basemap** (Natural Earth, public domain) | Self-hosted, offline, no rule broken, roughly 5–15 MB in the wheel. Useful to about zoom 8 — enough to identify a city, not a site. Solves *country* and *climate zone*; does not solve *draw your site*. |
| **(c) Opt-in external tiles** — the map is blank until the user explicitly enables a tile source they name | Preserves the rule as a *default* and makes the exception the user's informed choice. Costs a consent surface and a settings concept the app does not currently have. |
| **(d) Drop the rule for this feature** | Not recommended, and stated only so the option is on the record. The no-third-party-request rule is one of the reasons this tool is deployable inside institutions with restrictive networks. |

**Recommendation: (b) and (c) together.** Ship the bundled low-zoom basemap so
the feature works offline and delivers country and climate zone — the two
autofills that actually reduce user effort — and offer opt-in external tiles,
off by default, for users who want to draw a site boundary accurately and whose
network permits it. The packaged tool then makes no third-party request unless a
user has explicitly turned one on, which keeps the rule's substance while
admitting that a world-scale basemap cannot be bundled.

This needs the author's ruling because it is the first deliberate exception to a
rule that has been absolute for four releases.

### Decision 2 — Does an autofilled answer count as *supplied*?

The confidence mechanism (D-024) counts supplied fields, and `climate_zone` is
required. If the map fills it in, is that an answer?

- **Argument for yes:** the user chose the location, and a Köppen–Geiger lookup
  at a chosen point is not a guess — it is a cited classification.
- **Argument for no:** the tool's discipline is that confidence reflects what
  the *user* told it, and an inferred value that silently counts as an answer is
  how screening tools start overstating their own certainty.

**Recommendation: autofilled values count as supplied, but are marked as
autofilled in the input record, shown as such in the interface, and itemised in
the report's Inputs sheet** — the same treatment applied defaults since D-034.
A user who disagrees with the classification overrides it and the marking
disappears. The value is cited; the provenance is disclosed; nothing is hidden.
Autofill must **never** overwrite an answer the user has already given.

### Decision 3 — The Köppen–Geiger mapping is a methodology value

Mapping thirty Köppen classes onto the tool's six zones (`tropical_wet`,
`tropical_dry`, `arid`, `semi_arid`, `temperate`, `other`) is a judgement that
changes the climate adjustment factor, and therefore changes results. It needs a
cited source (`beck2018` / `beck2023` are the standard high-resolution
classifications, CC BY 4.0), an entry in the evidence tables, a documented
mapping table in `config/`, and a methodology version bump.

It also needs an explicit answer for the classes that do not map cleanly —
polar and boreal classes have no counterpart in a tool designed for urban heat.
**Recommendation: they map to `other`**, which is already the tool's neutral
climate condition, rather than being forced into `temperate`.

## Scope

1. **A map step** at the top of the questionnaire, skippable in one action. The
   questionnaire must remain fully usable without ever opening a map.
2. **Bundled datasets**: country boundaries and Köppen–Geiger classification,
   both under redistributable licences, both cited, both version-stamped, staged
   into the wheel exactly as `config/` and the bibliography already are (D-036).
3. **Autofill of exactly three inputs**, each marked as autofilled and each
   overridable.
4. **Provenance in the report**: the Inputs sheet distinguishes user-supplied,
   autofilled, and defaulted values.

## Out of scope

- Every other site input. Deriving canopy, imperviousness or LST from imagery is
  the GIS workflow (D-002), not this release.
- The city-scale hotspot mapping of [V2-VISION.md](V2-VISION.md).
- Any change to a scoring formula, an aggregation weight, or a typology value.

## Gates

Unchanged: 100% backend coverage, the D-017 evidence gates, golden scenarios,
ruff, mypy --strict, eslint, prettier, tsc, strict docs build, wheel smoke
check — plus two additions this release earns:

- **the no-third-party-request check must still pass for the default build**,
  whatever Decision 1 settles; and
- **a bundled-dataset licence check**, because two datasets now ship inside the
  wheel and the licence that permits that must be recorded where CI can see it.

A methodology version bump is required if and only if Decision 3 lands, which it
does under the recommendation above.
